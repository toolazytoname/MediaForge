## 结论

旧 P0 分支不是可直接合并的“完成版”。它把四类值得保留的工程修复，和一套已经被真人否定的项目驾驶舱交互，混在同一条提交历史里。

下一阶段应按能力挑拣，而不是 cherry-pick 或 merge 整个分支：保留缓存策略、OpenAI-compatible 文本中转回退、长请求超时、局部错误和提案不静默覆盖的原则；重写首页、文章编辑、预览和平台交付的界面。旧分支没有触及冻结的模型、数据库、源/发布 Adapter 契约，这是可安全复用其局部工程资产的前提。

## 按能力的落实建议

### 1. 缓存恢复

可复用 `426f6fa` 的后端缓存头和 router 一次恢复算法。需要重写的部分是全局提示的文案、位置和草稿恢复承诺：新首页与文章工作区必须真的持久化输入后，才能说“不会丢”。在 PF-01 前不要复制该提示 UI。

### 2. OpenAI-compatible 配置

`857218e` 是最小且隔离的后端修复，优先级高。它正确处理文本生成与设置页只配置图像中转的兼容情形。必须保持 `OPENAI_BASE_URL` 优先，不能以图片地址覆盖显式文本地址；连接地址只读取本地 secrets/environment，不能进入项目 sidecar、导出物或报告。

### 3. 编辑器与提案

`ProjectArticleEditor.vue` 的安全语义值得保留：初稿先提案、正文修改需要显式接受、版本恢复新增版本。但是其编辑控件是 textarea，选区仅依赖当前 DOM 字符串，建议是卡片而非 diff，无法满足局部锚点、图片批注、稳定选区和双栏审阅。PF-05/RV-01—RV-04 应新建文章本体组件，不复制该组件。

### 4. 视觉生成与失败恢复

`32c8686` 的生成超时与 `ff57fe5` 的局部错误隔离可保留为实现原则。旧视觉工作台要求“视觉计划/槽位/候选/选择”，不适合用户希望的文章内封面和插图。PF-04 应让图片从文章段落与上下文产生；单图失败显示在对应图片位置，重试不会重建文章或覆盖已选图片。

### 5. 平台 variants、预览与审批

旧 variants 的独立版本、防上游静默覆盖、选中视觉传递是可保留的安全资产；其先建两个平台稿、锁定、审批后才可阅读的产品顺序必须重构。阅读态要服务最终文章，Markdown 是正式导出，ZIP 是低优先级备份。旧 approval、stale、发布锁和角色记录保留在交付检查抽屉，不能成为写作的必经界面。

### 6. 超时、失败与状态恢复

旧分支只覆盖了部分请求 timeout、初稿失败手写、视觉局部错误和 iframe retry；未覆盖“首页输入刷新恢复”“生成过程断线后恢复同一任务”“文本和两张图片的部分成功”“提案刷新后仍能定位”“坏资料不阻塞好资料”。这些是 G1/G2 的新增测试和浏览器验收项，不能误判为已解决。

## 合并/实现顺序

1. 不合并 `codex/creator-workflow-p0`；以 `ac232fe` 为新实现基线。
2. PF-01 前先从 `426f6fa` 选择性实现并测试缓存恢复（若主分支尚无对应修复），同时审阅 `857218e` 的 relay fallback。
3. PF-01—PF-05 按新 UX 原型新建首页和文章工作区；只调用既有 sidecar、版本、视觉和 variants 服务，不把旧 `Projects.vue` 驾驶舱复制回来。
4. RV 阶段重做批注锚点与 diff；仅继承“不静默覆盖”和可恢复版本不变量。
5. DL 阶段再接入旧 variants / preview / approval 安全能力，放进次级交付界面；真实发布继续禁止。
6. 每一步重新构建 `frontend/dist/`，不从旧分支挑 hash 资源文件。

## 必须先补的回归证据

PF-00 的“测试先行”审查结果：旧分支已经有两个有价值的自动化回归——缓存策略和 OpenAI relay fallback；空研究可起草测试也证实了不能把资料完整度当硬门槛。以下旧浏览器问题尚无充分的端到端自动化或真人新路径证据，后续任务必须先写测试：

- stale chunk：首次恢复、第二次给可见动作，且首页/文章未保存输入的持久化是真实的；
- 文本、封面、两张插图在 provider 超时或其中一项失败时保留同一篇文章与已完成结果；
- AI 初稿、全文意见、局部意见在刷新和并发点击后不会丢失、重复执行或覆盖正式稿；
- 文章内图片故障只影响该图片，不产生全页错误；
- 平台版本仍是独立可编辑版本，主稿晚改不会静默覆盖；
- 预览返回非 2xx 或内容错误时可明确失败，不能只依赖 iframe load；
- 审批/导出/发布安全继续存在，但首屏和生成主路径不依赖它们。

## 未解决风险

1. 旧 P0 有历史浏览器记录，但本审计未重跑其服务；这些记录只能说明当时的局部行为，不能作为当前环境或新交互通过证据。
2. `OPENAI_IMAGE_BASE_URL` 是否同时支持 chat/completions 是中转站能力假设。fallback 已有单元测试，却仍需在用户本地配置下做一次真实文本调用；不得在报告中记录地址、token 或响应内容。
3. iframe preview 的 error 事件覆盖不完整，且无法代表内嵌图片、排版和引用真实可用；新阅读态需由显式内容状态和浏览器检查验证。
4. 旧项目 UI 将研究、视觉、variants、审批绑在一个大型 `Projects.vue`。直接迁移任何大段模板或状态会把被否定的导航重新带回新首页。
5. 旧分支与当前基线之间包含生成的 `dist` 大范围变化。若用粗粒度 merge，会制造无关冲突并掩盖源代码审阅。
